# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`terraforme` is a Rust CLI (Linux and Windows) that installs and manages three extensions for AI agents — [RTK](https://github.com/rtk-ai/rtk) (token savings), [AI Memory](https://github.com/akitaonrails/ai-memory) (cross-session memory) and [AI Jail](https://github.com/akitaonrails/ai-jail) (OS sandbox) — and launches the agent (currently only Claude Code) in modes that toggle the first two, optionally inside the jail. User-facing text, doc comments and code comments are in **Portuguese**; commit messages must be in **English**.

## Commands

```bash
cargo run -p terraforme-cli -- --help        # or: pnpm cli --help
cargo build -p terraforme-cli --release      # target/release/terraforme
./install.linux.sh                           # release build + install to ~/.local/bin (--update: git pull first; --dist; --uninstall)
.\install.windows.ps1                        # same on Windows (-Update/-Dist/-Uninstall), into %LOCALAPPDATA%\Programs\terraforme\bin + user PATH; UTF-8 BOM required (PowerShell 5.1)
terraforme restart                           # kills every terraforme-mcp (also orphans), starts the new one, reopens the pet; install scripts ask for it at the end (`upgrade --restart` / `TERRAFORME_RESTART=1` skips the prompt)
terraforme plugin install pet                # plugins from other repos (list/install/update/remove; `owner/repo` for third-party)
terraforme pet                               # floating window with the mascot (Linux and Windows, plugin; `terraforme config --pet true` opens it with `terraforme cli`)
terraforme upgrade                           # execs <repo>/install.linux.sh --update (install.windows.ps1 -Update on Windows) (repo = CARGO_MANIFEST_DIR/../.. at build time, or --repo / TERRAFORME_REPO); without that repo (release binary) it runs the install.sh / install.ps1 below from GitHub
curl -fsSL https://raw.githubusercontent.com/Augustowtg/terraforme/main/install.sh | sh    # release binaries, no Rust (Linux x86_64/aarch64 musl)
irm https://raw.githubusercontent.com/Augustowtg/terraforme/main/install.ps1 | iex         # same on Windows; install.ps1 must stay ASCII and wrapped in `& { }` (runs in the user's session: no `exit`)

cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test -p terraforme-core toml_round_trip   # single test (name filter)
```

`.github/workflows/ci.yml` runs fmt, clippy and tests on `ubuntu-latest` and `windows-latest` only on `v*` tags (new versions) and on manual `workflow_dispatch`, not on pushes or PRs, so run `cargo fmt`/`clippy`/`test` locally before opening a PR; it is the only place `#[cfg(windows)]` code is compiled (cross-checking for `x86_64-pc-windows-msvc` locally fails on `ring`, which needs `lib.exe`).

`release` has no LTO on purpose (fat LTO + 1 codegen unit left the last step, the `terraforme` binary, compiling on a single core for ~35s+, looking stuck at 181/182); the `dist` profile keeps that for distribution builds.

Toolchain is pinned to Rust 1.98.0 (edition 2024) via `rust-toolchain.toml`. Node/pnpm exist only for git hooks: `pnpm install` at the root enables Husky. `pre-commit` runs `cargo fmt --check` and `cargo clippy -D warnings`; `commit-msg` runs commitlint.

## Versioning and changelog

Every change that ships (feature, fix, behavior or build change — not pure refactors/docs) bumps `[workspace.package] version` in the root `Cargo.toml` (SemVer: minor for features, patch for fixes; both crates inherit it, refresh `Cargo.lock` with `cargo metadata` or a build) and adds a `## X.Y.Z - YYYY-MM-DD` section at the top of `CHANGELOG.md` (Portuguese, Keep a Changelog headings `Adicionado` / `Alterado` / `Corrigido` / `Removido`). Several changes in the same unreleased session go into the same new version. `install.linux.sh` prints the sections newer than the previously installed version after an update, so keep the `## <version>` heading format.

## Releases

`.github/workflows/release.yml` runs on a `v*` tag (must equal `v` + the `Cargo.toml` version): builds `terraforme` + `terraforme-mcp` with the `dist` profile for `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl` (`musl-gcc` for `ring`) and `x86_64-pc-windows-msvc`, packs `terraforme-<target>.tar.gz`/`.zip` + `.sha256`, and creates the GitHub Release with that version's `CHANGELOG.md` section. `install.sh`/`install.ps1` download from it, so keep the asset names in sync.

## Commits

Conventional Commits, `<type>(<scope>): <subject>`. Rules in `commitlint.config.mjs`: allowed scopes are `core`, `cli`, `deps`, `ci`, `docs`, `config`, `release`; subject lower-case; header ≤ 100 chars; any non-ASCII character or common Portuguese word (e.g. `para`, `uma`, `cria`) is rejected.

## Architecture

Cargo workspace with three crates (the floating window is a plugin in its own repo):

- **`crates/terraforme-core`** — all logic. The CLI is just a shell around it. The optional `clap` feature derives `clap::ValueEnum` on public enums (`Extension`, `Provider`, `Mode`) so the CLI can use them directly as arguments.
- **`crates/terraforme-cli`** — the `terraforme` binary: clap definitions and output formatting in `main.rs`, plus the TUI in `term.rs`.
- **`crates/terraforme-mcp`** — the shared `terraforme-mcp` daemon (axum, JSON-RPC over HTTP on `127.0.0.1`), started on demand by `terraforme cli` (`mcp::ensure_running`, lock file `<data dir>/terraforme/mcp.lock`) and shut down `[mcp] grace_seconds` (default 5s) after the last client leaves (or 30s after start with none). A daemon only writes the lock if no other healthy one holds it (`LockFile::claim`, else it exits) and only removes its own (`LockFile::release`). `/heartbeat` answers 404 for an unknown client; the TUI's heartbeat thread then (or when the daemon is gone) calls `ensure_running`, re-registers the client and sends `Msg::Reconnected`, which re-registers every instance (`Agent::register`) — running agents keep the old port in `--mcp-config` until restarted. Every TUI registers itself (`/register` + heartbeat, with its control server address) and each agent instance (`/instances/register`, unregistered on `Agent` drop); the `hub` keeps instances from all spaces with a handle `<space or dir>/<agent>-<n>` and the message log. Tools (`docs/MCP/mcp.feature.md`): `list_instances`, `send_message` (delivered as `POST /message` to the target TUI's control server, which types it as a prompt via `Agent::queue`), `open_instance`/`delegate_task` (`Hub::open`: the daemon picks the instance id, sends `POST /open` to the caller's TUI, which spawns it with that id (`App::open_requested`, no focus change) and queues the text; the call returns once the instance registers, 10s timeout; `delegate_task` then waits up to 30 min (`Hub::wait`): the worker's `send_message` back to the caller resolves the waiter (`Hub::resolve`) and becomes the call's `result` instead of being typed; on timeout/cancel it falls back to a prompt; `delegate_task` with `to` types a delegation prompt into an open instance and waits the same way), `close_instance` (`POST /close`, kills the process; never the caller) and `spawn_subagent` (`claude --print`, result returned in the call). Prompts are delivered by `Agent::deliver_pending` once the agent enabled bracketed paste (or 20s passed) and its output is quiet for 500ms: pasted, then Enter 300ms later (same burst = treated as paste, not submit). Only Claude gets the MCP so far; what's missing for other agents is in `ROADMAP.md`. Each instance gets the server through `Adapter::mcp_args` (Claude: `--mcp-config` with `x-client-id`/`x-instance-id` headers; `list_instances`/`send_message`/`open_instance`/`delegate_task` are pre-allowed in the session `--settings`, `close_instance` asks); with AI Jail, `jail::wrap` forwards the daemon port, so `run_term` starts the daemon before building the command. `[mcp] ui` enables the web UI at `/ui` (also `GET /`; main page "Terraforme instâncias", a `Space | Agentes` table per `docs/tui/webserver/webserver.feature.md`) (+ `/api/state`, `/api/send`, `/api/usage` with the `history` totals), read from `config.toml` on every request and limited to local `Host`/`Origin`. Each TUI also reports every instance's `pet::Activity` (`POST /instances/state`), served to the floating window by `GET /pet/state`; `POST /pet/focus` forwards `POST /focus` to the owning TUI's control server (both local-only, independent of `[mcp] ui`).
- **`terraforme-pet` plugin** ([Augustowtg/terraforme-pet](https://github.com/Augustowtg/terraforme-pet), was `crates/terraforme-pet`; depends on `terraforme-core` by git, so `core::pet`'s public API is a contract with it) — the `terraforme-pet` floating window (eframe/egui, glow; Linux and Windows — on other OSes `main` just points to `ROADMAP.md`; the GUI deps are `cfg(any(target_os = "linux", windows))` and on Windows it is a `windows_subsystem = "windows"` app, so errors also go to a notification). Undecorated, transparent, always-on-top window with the tatu-peba mascot from the plugin repo's `assets/*_strip.png` (4 frames of 48×34, embedded with `include_bytes!`, drawn ×3 with `TextureOptions::NEAREST`); the mood is the most urgent instance state (sleeping/happy/tired/attention/notification/danger). Polls `pet::instances()` every second, shows a bubble + `pet::notify` (`notify-send`; a PowerShell toast on Windows, text passed in `TERRAFORME_NOTIFY`) when an instance turns `Done`/`Waiting`, and a click opens the menu of all instances (`pet::focus`). Started by `terraforme pet` or `[tui] pet` (`pet::start`, single instance via `<data dir>/terraforme/pet.lock`). Installed with `terraforme plugin install pet` (glibc binaries from its own release: musl can't `dlopen` X11/Wayland/GL; a `.zip` for `x86_64-pc-windows-msvc`); Optional and off by default (`[tui] pet = false`): no install script installs it, and they (and `terraforme upgrade`) only run `terraforme plugin sync`, which updates installed plugins whose `Known::enabled` check passes (pet: `config.tui.pet`), so a disabled pet stays as it is; `install.linux.sh` installs the GNOME extension only when `plugin enabled pet` (hidden, exit code) succeeds.

Core modules:

- `plugin` — optional programs published in their own repos (`terraforme plugin list|install|update|remove`). A `Manifest` (`terraforme-plugin.toml` at the repo root: `name`, `bin`, `repo`, `platforms`, `min_terraforme`) comes from the `KNOWN` registry (official plugins; adding one = one entry) or, for `owner/repo`, is fetched from `raw.githubusercontent.com/<repo>/HEAD`. `sources()` is the factory of `Source`s available on this machine, tried in order by `install`: `Release` (`<repo>/releases/latest/download/<bin>-<target>.tar.gz` + `.sha256`, target `<arch>-unknown-linux-gnu`/`-apple-darwin` with `curl`, or `<arch>-pc-windows-msvc` `.zip` via PowerShell (`RELEASE_PS1`, values in `TF_*` env vars)) then `Cargo` (`cargo install --locked --git`, built in a temp `--root`). Binaries go to `install_dir()` (`~/.local/bin`; the `terraforme` dir on Windows, where `replace` renames a running `.exe` to `.old` instead of overwriting it) and installed manifests to `<config dir>/plugins.toml`; `locate(bin)` finds a plugin next to `terraforme`, in `PATH` or in `install_dir()`.
- `status` — `Component`/`State` (Installed / Conflict / NotInstalled) and PATH lookup + `--version` parsing helpers shared by the other modules. On Windows `find_in_path` follows `PATHEXT` (npm installs `.cmd` shims, e.g. `opencode.cmd`), and `std::process::Command` only completes `.exe`, so always spawn the returned full path (`status::command(bin)`), never a bare name.
- `platform` — the OS-specific process bits, the only place that uses `windows-sys`: `is_pid_alive` (`/proc` / `OpenProcess`), `ignore_ctrl_c` (on Windows there is no `exec`, so the parent waits on the child and must ignore the console's `Ctrl+C`), `kill_all` (every process with an executable name, for `terraforme restart`: `/proc/*/comm` + `kill` / `tasklist` + `taskkill`) `kill` (one PID: `kill` / `taskkill`, forced only if the window does not close), `no_window` (`CREATE_NO_WINDOW`, for children of the windowless pet), `allow_foreground` (`AllowSetForegroundWindow(ASFW_ANY)`, called by `pet::focus`) and `detach` (the MCP daemon gets no console on Windows and its own process group on Unix, so closing the launching terminal doesn't kill it).
- `extension` — install/update/delete for RTK and AI Memory using each project's official install scripts and their own subcommands (AI Jail has no install script: the release tarball is downloaded, checked against its `.sha256` and installed to `~/.local/bin`; update/delete refuse a copy outside it, e.g. Homebrew); external commands inherit the terminal. Also defines `Report`s (e.g. `rtk gain`, `ai-memory status`), which run the extension binary with `NO_COLOR` and return ANSI-stripped text.
- `usage` — Claude Code token consumption parsed from the transcripts in `~/.claude/projects/<cwd with non-alphanumerics → '-'>/<session>.jsonl` (respects `CLAUDE_CONFIG_DIR`). One response spans several lines, so entries are deduplicated by `message.id` + `requestId`. Subagent transcripts live in `<session>/subagents/agent-<id>.jsonl` (same `sessionId`, plus `agentId`; type/description in the sibling `.meta.json`). OpenCode delegates to `opencode stats --json` for project/day and global/day/week aggregates; its CLI does not expose a rolling five-hour window, current-session token totals or token breakdowns by subagent.
- `limits` — how much of the usage limits is left, standardized by terraforme: each agent's `Adapter::quota()` returns the plan limits in the `Quota` shape (Claude reads them from `api.anthropic.com/api/oauth/usage` — OAuth token read from `<claude dir>/.credentials.json`, never refreshed by us — and `limits` caches the result for 60s), and terraforme converts them to `Limit`s (percentage used, tokens, reset time), falling back to the config `[budget]` compared with transcript totals when the agent reports none. OpenCode exposes no plan limits and no five-hour window, so only the weekly budget entry is shown there.
- `history` — token consumption history per space × agent in SQLite (`rusqlite` bundled) at `<root>/usage.db` (`space::root`): one row per session (`key` = `<agent>:<session id>`, or pid/instance/launch time without one), totals replaced on every write; `History::totals` sums them per space × agent (24h / 7 days by last update, plus all time). The TUI writes every instance's `usage.session` every 60s (`RECORD_EVERY`), when an instance closes/restarts and on exit (`App::record_usage`); OpenCode reports no session total, so it is not recorded. Shown in the Consumo `Spaces` sub-tab and in the MCP web UI (`/api/usage`). A `launches` table keeps one row per folder where `terraforme cli` was opened (`record_launch` in `Choice::resolve`, also under `--plain`; a failure is only a warning), listed by `terraforme --historico` (alias `--history`), split into saved spaces (most recent launch in each, matched with the current `spaces.toml`) and recent folders outside any space.
- `pet` — floating window support: `Activity` (idle/working/done/waiting) and `Tracker`, the heuristic the TUI feeds with PTY output and user input (output for ≥2s with no keystroke in the last 1.5s = working, 4s of silence after = done, BEL/OSC 9/777 = waiting, input or opening the sub-tab = seen; the first 5s after launch are ignored); the HTTP client used by `terraforme-pet` (`instances`, `focus`), `notify` (`notify-send`) and the pet lock/start helpers. `platform::raise_terminal` brings the TUI's terminal window to front: first via the GNOME Shell extension in `assets/gnome-shell/terraforme@augustowtg.github.io` (`gdbus call … org.gnome.Shell.Extensions.Terraforme.Activate` with the ancestors' PIDs; it switches workspace and unminimizes; X11 and Wayland; installed/enabled by `install.linux.sh`, loaded by GNOME only after re-login on Wayland), then on X11 (`$WINDOWID` or the ancestors' windows via `xdotool search --pid`, then `xdotool windowactivate`/`wmctrl -i -a`); on Windows `SetForegroundWindow` on the console's owner window (Windows Terminal), the console itself (conhost) or the first ancestor with a visible window (e.g. VS Code), which works because the pet called `allow_foreground`; no-op on other Wayland compositors.
- `chat` — Middleware (experimental, `[tui] middleware`): `ChatEvent`, the agent-agnostic shape of the agent's structured output, plus Claude Code's `stream-json` (`CLAUDE_ARGS`, `claude_input`, `claude_events`; subagent lines with `parent_tool_use_id` are skipped) and its SDK control requests on the same pipes: `claude_initialize` (sent at start, its response lists the `/` commands → `ChatEvent::Commands`) and, with `--permission-prompt-tool stdio`, `can_use_tool` → `ChatEvent::Permission`, answered by `claude_permission` (`Answer::Once`/`Always` = the suggested `addRules`/`Deny`); other control requests get an error `ChatEvent::Reply` right away. Agents opt in through `Adapter::chat_args`/`chat_input`/`chat_events`/`chat_start`/`chat_permission` (only Claude so far).
- `config` — `Config { provider, mode, jail, budget, mcp, tui }` in `~/.config/terraforme/config.toml` (`%APPDATA%\terraforme` on Windows; respects `XDG_CONFIG_HOME`).
- `space` — named working directories (`Spaces`, a name → path `BTreeMap`) in `<config dir>/spaces.toml`, kept out of `config.toml` because `Config` is `Copy`. `terraforme space` picks one (list number or name) and `exec`s the user's shell there (`space::shell`, sets `TERRAFORME_SPACE`), since a process can't change its parent shell's cwd; `--path` prints the dir instead (prompts go to stderr) for a `cd "$(…)"` shell function. Per-space `Preferences` (optional `agent`/`mode`/`jail`/`account`) live outside the project in `<root>/<space name>/preferences.toml` (`space::root`: `~/.terraforme` on Linux, `%APPDATA%\.terraforme` on Windows, where an old `%USERPROFILE%\.terraforme` is moved on first use; `TERRAFORME_HOME` overrides; `terraforme status` lists it with the config and data dirs; space names can't contain `/`/`\`), set with `terraforme space <name> --agent/--mode/--jail/--account/--reset` and moved/removed with the space; `Spaces::load` migrates the legacy `<space dir>/.terraforme/preferences.toml`. `terraforme cli` uses the deepest saved space containing the cwd (`Preferences::find`) and resolves CLI flags → space preferences → project `.ai-jail` (jail only) → `config.toml`.
- `jail` — AI Jail integration: `default_config()` written to `~/.ai-jail` only when absent (on install and on a jailed launch), and `wrap()`, which turns the agent command into `ai-jail --no-save-config <maps> -- claude <args>`. Maps are passed per launch, never saved: each mode extension's plugin dir and binary (plus its symlink target dir) read-only, `~/.local/share/{rtk,ai-memory}` writable, and `--forward-port` for every `127.0.0.1:`/`localhost:` port found in the plugin's `hooks.json`/`.mcp.json` (AI Memory's local server). Requires ai-jail ≥ 2.9 (`--forward-port`) and `bwrap` on Linux. There is no AI Jail on Windows (`jail::is_supported`): a jail implied by a project `.ai-jail`, the config or a space is dropped with a notice, and only an explicit `--jail` errors. `ensure_project()` creates the project `.ai-jail` (`ai-jail --init <agent>`) when missing (never in `$HOME`, where it is the global file); it is called only explicitly via `terraforme extension ai-jail --project` — `terraforme cli` does **not** auto-create `.ai-jail` on launch. Never pass `--no-status-bar` on the CLI: ai-jail persists status-bar flags into `~/.ai-jail`.
- `agent` — `Provider` and `Mode` (`none` = no extension, `eco` = RTK, `high` = AI Memory, `hybrid` = both; AI Jail is never part of a mode — `Mode::uses` is false for it) plus `CliMode`, the start presets shown by `terraforme config --cli` (`eco` = RTK, `high` = AI Memory, `security` = AI Jail with no extensions, `custom` = the user picks the extensions; `preset()`/`of()` map them to `(mode, jail)`). Each agent is an `Adapter` trait object (`Provider::adapter()`, `None` = not implemented yet, e.g. Cursor): `bin`, `setup(mode)` (returns the agent args + per-extension plugin dirs), `session_args`/`picks_session`, `usage`, `quota` and `forget(ext)` (cleanup on extension delete). `agent::prepare()` is agent-agnostic: it checks the extensions, calls `setup`, appends passthrough args and wraps with `jail::wrap`, building the `std::process::Command` that `terraforme cli` runs in the TUI (or directly, with `exec`, under `--plain`). The TUI only talks to the agent through the adapter. To add an agent: a module in `agent/` implementing `Adapter`, a `Provider` variant, and the mapping in `Provider::adapter`. Claude Code lives in `agent/claude.rs` (it delegates to `usage::collect` and implements `quota()` with the plan's usage API, both Claude-specific).

### How modes work with Claude Code (`agent::claude`, `Claude::setup`)

This is the non-obvious part and it touches the user's global Claude config:

1. RTK/AI Memory hooks are **moved out** of `~/.claude/settings.json` (backup saved as `settings.json.terraforme-bak`) into per-extension local plugins at `~/.config/terraforme/plugins/terraforme-<ext>/hooks/hooks.json`. This happens on every launch, so if `rtk init -g` / `ai-memory setup` puts the hooks back in the global file, they are moved again. The global file is only rewritten after the plugins have been written.
2. For each extension used by the mode, `--plugin-dir <plugin>` is passed to `claude`.
3. The global AI Memory MCP server in `~/.claude.json` is **not modified**: it is blocked for the session via `--settings '{"deniedMcpServers":[{"serverName":"ai-memory"}]}'`, and the AI Memory plugin gets a copy of it in its `.mcp.json` (as server `memory`) when the mode uses it.
4. Extra args after `--` are passed through to `claude`.
5. With `jail` (`config.jail`, overridden by `--jail`/`--no-jail`), the whole command is wrapped by `jail::wrap`, and the TUI shows AI Jail reports in the Extensões tab.

As a result, running `claude` directly (without terraforme) gives a session without the RTK and AI Memory hooks.

### `terraforme cli` terminal (`term.rs`)

ratatui TUI with a tab bar on top: one agent tab (`claude` or `opencode`) whose sub-tabs, on a second line, are the agent instances (`claude 1`, `claude 2`…; `--instances/-n N` at launch, `Ctrl+Alt+N`/`F12` opens another, `Ctrl+Alt+W`/`Shift+F12`/`F24` kills the active one, `Ctrl+Alt+R` restarts it in place, max 9; a sub-tab disappears when its process exits and the TUI quits when the last one does), `Consumo` (sub-tabs Limites / Tokens / Subagentes / Spaces — Spaces is the `history` table, not per instance — auto-refreshed every 5s for the focused instance — Claude uses transcripts and OAuth limits; OpenCode uses `opencode stats --json` for daily/project and weekly aggregates, without current-session or rolling five-hour detail — Antigravity uses the transcripts `agy` writes under `~/.gemini/antigravity-cli/brain` and the account limits it reports with `agy -p "/usage" --output-format json` (one weekly bucket per model group, with its reset time); the Limites view draws one `Router <agent>` block per agent with an open instance (focused one first; `format_routers`) and, in each, one Claude-style bar per limit: a green bar starting full at 100% that shrinks as tokens are consumed, with the total token limit, the time left and the local reset date (`DD/MM/AAAA - HH:MM`, `chrono`) on the header; followed by the RTK `Report`s when the mode uses RTK, not auto-refreshed), `Extensões` only when there are non-RTK reports (AI Memory, AI Jail; `reports(tab, extensions)` splits them), and `Config` (always last: a `Form` laid out per `docs/tui/config/config.feature.md` — sections Agente / Orçamento / Plugins · config global / Avançado, fields from `Form::fields()` (the AI Jail/RTK/AI Memory boxes only when the mode is `custom`, a `CliMode` preset) — that edits `config.toml` (or the space `preferences.toml` for agent/mode/account) and saves on every change; the 7-day/daily budgets are derived from the 5-hour one; `[tui] mouse`/`copy_on_select` apply live; the agent field is labeled `Router` and its change is deferred (`Form::router`) until the selection leaves the field or the tab (`Form::leave_router`, checked in `Form::key`, `App::click_form` and `App::select`), then it calls the `Options::relaunch` closure (`Choice::resolve` again) and opens an instance of the new agent while old ones keep running — each `Agent` keeps its own `name`/`adapter` — and a mode/account change marks `App::stale` so the next instance re-resolves; clicking the UI row or `o` opens the web UI via `platform::open_url`). Each instance runs in its own `portable-pty` pseudoterminal (on Windows a ConPTY created with `PSEUDOCONSOLE_INHERIT_CURSOR`: it sends `ESC[6n` at start and blocks the agent until `Agent::answer_cursor_queries` replies, and its reader never hits EOF when the child exits, so the event loop also polls `Agent::exited`), resized to the real screen before every draw (`App::fit`, not only on `Event::Resize`), rendered with `vt100` + `tui-term` (5000-line scrollback) and keeps running while another tab is open; non-agent tabs load their content on a background thread when selected. The kitty keyboard protocol (`DISAMBIGUATE_ESCAPE_CODES`) is pushed when `supports_keyboard_enhancement()` says so (`App::enhanced`), so `Ctrl+Shift`/`Ctrl+Alt` combos arrive distinct. Tabs are built with the **registry** design pattern: each tab is a single `TABS` entry (`TabSpec` — order in the menu, name, `Ctrl+Shift+F<n>` shortcut, own sub-tabs and `TabKind`: `Agent`/`Content`/`Form`), and menu, shortcuts, help and opening all read that list (`spec(tab)`), so no `match tab` is scattered around; adding a tab means adding an entry. Tabs: `Ctrl+Shift+F1` (Agent), `Ctrl+Shift+F2` (Consumo), `Ctrl+Shift+F3` (Extensões, only when the mode shows that tab) and `Ctrl+Shift+F4` (Configurações), plus `Ctrl+Shift+←/→` (`tab_step`/`App::step_tab`; plain `←/→` in the Consumo/Extensões views) for the neighbouring tab; the menu (`App::draw_menu`, laid out per `docs/tui/tui.feature.md`) is the blocks `Terraforme` `Agente (<agent>)` `Consumo` `Extensões` `Configurações` `Sair` (same style as `Terraforme`: the active tab green like it, the others gray) with `⌃⌥K Atalhos` right-aligned, and a click on it opens the tab or quits (`App::menu_hit`, `MenuItem`); all extra/duplicated tab shortcuts (`Shift+1/2`, `F1/F2`, `Ctrl+Shift+1..9`, `Shift+F1..F9`, `Ctrl+Shift+Tab`, `Shift+Tab`) are disabled so `Shift+Tab`, digits and function keys reach the agent. Sub-tabs, the same in every tab (`App::pick`/`App::cycle`/`App::open_sub`): `Ctrl+Alt+Tab` (Shift = back; legacy arrives as `Alt+Tab`) and `Ctrl+PgUp/PgDn` cycle, `Ctrl+Alt+1`–`9` / `Alt+1`–`9` jump (`sub_tab_number`, digits only — symbols would catch AltGr on Windows), and in the agent tab a number past the last instance opens a new one. TUI commands are `Ctrl+Alt+letter` (`n w r c s k`; `k` = shortcut list in a `Popup`), chosen to dodge Linux desktop bindings (`Ctrl+Alt+T/L/D/Del/F*/arrows`) and letters whose legacy control byte collides with another key (`Ctrl+Alt+M` = `Alt+Enter`, `H` = Backspace, `I` = Tab, `J` = LF). `Ctrl+←→` is not bound (it reaches the agent for word movement). Every sub-tab bar is drawn by `sub_tab_spans` (`⌃⌥N label`, or `⌥N` without the protocol), `F10` quits. Key events are translated to xterm byte sequences in `key_bytes` (which respects application-cursor mode). Mouse capture is on by default (`[tui] mouse`; `Ctrl+Alt+S` toggles it at runtime) so the wheel scrolls (otherwise the terminal turns it into arrows, which reach the agent as prompt history): in the agent tab it is forwarded as a wheel event (`wheel_bytes`, the agent's encoding) when the agent enabled mouse reporting, sent as arrows on its alternate screen, and otherwise scrolls the `vt100` history; in the other tabs and popups it scrolls the content. Left-drag in the agent tab makes a `Selection` (screen cells, highlighted over the rendered buffer, read with `contents_between`) that is copied on release (`[tui] copy_on_select`) by `clipboard()`: OSC 52 plus, on Linux, `wl-copy`/`xclip`/`xsel` (VTE ignores OSC 52); `Ctrl+Alt+C` copies the selection, the visible screen or the open tab's text. Each `Agent` parses output with `vt100::Parser<Signals>` (callbacks catch BEL and OSC 9/777 notifications, not OSC `9;4` progress) and keeps a `pet::Tracker`; user keys/paste/wheel go through `Agent::input` (marks it seen), changes are reported to the daemon by `Agent::report`, and the control server's `POST /focus` (`Msg::Focus`) opens the instance's sub-tab and calls `platform::raise_terminal`. Short feedback goes to `App::status` (bottom-right, `STATUS_TTL`, drawn over the footer). The last screen row is a footer (`App::draw_footer`, so `body_size` leaves 3 rows out): the current prompt's tokens on the left and the focused instance's session total on the right; the terraforme session total (every instance since launch, closed ones included, `App::spent`) is right-aligned on the sub-tab line (`App::spent_line`, the shortcut hint is dropped when it doesn't fit) and on the view block title. They come from `Adapter::live_usage` (Claude: `usage::live`, reads only the session transcript + its subagents; `Live` = session / since launch / since the last typed `user` line), polled on a thread every 5s (`LIVE_EVERY`, `App::poll_live` → `Msg::Live`). With `[tui] middleware` (Config field `Middleware (Experimental)` in the Agente section, always in `config.toml`, applied to the next instances), `Agent::spawn` runs agents that have `Adapter::chat_args` with pipes instead of a PTY (`master: None`, stdout lines → `Msg::Output`, stderr → `Msg::Stderr`) and the instance gets a `Chat` (`crates/terraforme-cli/src/chat.rs`, per `docs/tui/agente/agente.feature.md`): messages on top, input box at the bottom, keys go to `Agent::chat_key` instead of `key_bytes`, `Agent::queue` sends MCP messages straight away, `Ctrl+Alt+C` copies the transcript. Lines to the agent go through `Chat::outbox` (flushed by `Agent::flush_chat`). Agent replies are rendered by `markdown.rs` (headings, lists, quotes, inline code/bold/links, fenced code highlighted with `syntect` + `two-face` (bat syntaxes, `regex-fancy`) using the VS-Claude palette), cached per entry by width/text length. The input box completes `/` commands (`rank_commands`) and `@` files (`list_files`: `ignore` walk of the cwd, read on the first `@`); a pending permission replaces the input box (`1`/`2`/`3`, `↑↓`+`Enter`, `Esc` denies) and marks the instance waiting. With middleware on, the agent tab is labeled `Middleware` and every router's instances are its sub-tabs. Notices/warnings from `prepare()` are shown in an initial popup, because the alternate screen would hide anything printed before it.
